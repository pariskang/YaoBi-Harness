# 会诊子体与技能库

## 为什么要拆成子体

同一份病历放在一个上下文里推理，模型会给出一个听起来自洽的答案——**分歧被平均掉了**。
而临床上最有价值的信息常常恰好在分歧里：药师看到的抗凝风险，骨科主任不一定会主动想到；
康复科看到的恐动倾向，疼痛科不会写进机制分析。

所以让几位"会诊者"各带自己的专科视角独立运行，最后**保留分歧**而不是消解它。
架构上参考了 Grok Build 的 subagent 设计（独立上下文 + 粗粒度能力模式 + 行为层 persona +
声明式 I/O 契约 + 深度上限 1），四处为临床做了改写。

## 四条改写

### 1. 任何子体都不出处方

`consult_mode` **只能收窄**技能的工具授权，不能扩大。即使最宽的 `advisory` 模式，
`formula_composition_search` / `herb_dose_distribution` / `physician_review_submit`
三个工具对任何会诊子体都不可达。

这一点在 `SkillSpec.effective_tools()` 里用交集而非并集实现，
所以一个自定义 persona 文件**无法通过声明把自己授权进去**。测试逐模式校验了这条
（`test_no_mode_reaches_a_prescriptive_tool`）。

而且成员 broker 是**包装**而非替换外层 broker：运行的角色与风险模式的限制仍然全部生效。
患者角色的急症运行里，成员即使 mode 允许也拿不到方剂工具。

### 2. 深度上限 1

会诊不能再开会诊。既为可审计，也为不产生没人能复核的转诊链。

### 3. 预算是切分的，不是共享的

每位成员拿到父预算的一个切片。烧完就降级为无意见，**不会挤占后面的剂量安全检查**。
切片同时把消耗**回记到父预算**（`_ChargebackBudget`），否则控制台会报告一次实际用了
20 次调用的运行只用了 4 次，父预算的上限也就不再有意义。

### 4. 合议是"最保守优先"，不是多数票

这是与常见多智能体投票最重要的一处不同。

多数票适合判断"这个 bug 是不是真的"，**不适合判断"这是不是马尾神经综合征"**——
一位会诊者看到急症，其分量压过四位没看到的，因为两个方向的代价完全不对称。

所以：

* 最终紧急度取**所有成员中的最高值**（`routine < expedited < urgent < emergency`）；
* 关切事项取**并集**，不做筛除；
* 一致程度只作为**信息**呈现（"3/5 位会诊者给出该紧急度"），**不作为过滤条件**。

推论：**成员上调紧急度不会被投票否决**，所以提示词里明确告诉它不要因为
"别人可能不同意"而保留意见。

再往上一层还有一道限制：`ConsultPanelAgent` 只能**升级**运行的风险模式，
不能降级。五个模型一致认为规则判定的急症其实是常规，什么也不会改变。

## 五位会诊者

| Persona | 视角 | consult_mode |
| --- | --- | --- |
| `ortho_attending` 骨科主任 | 不漏诊急症：逐条写"已排除/未排除/无法判断"，判断是否需要影像及哪一种 | `screening` |
| `pain_specialist` 疼痛科 | 机制：外周痛感受性 / 神经病理性 / 中枢敏化 | `screening` |
| `rehab_specialist` 康复科 | 功能与暴露：可执行到"每天几次、做多久、什么感觉时停" | `evidence_only` |
| `tcm_orthopedist` 中医骨伤 | 辨证与四诊缺口；只给治法方向，不给方剂克数 | `evidence_only` |
| `clinical_pharmacist` 临床药师 | 用药安全：14 组骨科高频风险逐条核对 | `screening` |

**召集是规则决定的，不是模型决定的**：药师在有用药清单时必须到场，
这件事不能依赖模型注意到。模型的自主性在每位成员**内部**——它自己选工具、自己取证、
自己组织专科意见。

召集规则：药师与骨科主任默认到场；主诉带四诊或医师角色加中医骨伤；
带麻/无力/放射/灼/电加疼痛科；病程以月/年计或有 ODI 加康复科。

## 开关与成本

**默认关闭。** 五个子体会让一次运行的 token 成本翻几倍，这是操作者的决定，
不该在账单上被发现。

```bash
python -m yaobi_harness run --complaint "…" --role physician --panel
```

控制台「单次运行」里是「召集多学科会诊」复选框，说明里写明 token 开销显著增加。

`ConsultPanelAgent` 仍在 `AGENT_CATALOG` 里，所以**LLM 规划器可以自己决定召集它**——
这正是这套设计要的自主性；规划提案仍要过校验层。

## 技能库：SKILL.md

技能承载两样东西，方向相反：

* **策略**——工具授权、输出契约、角色限制。应该集中在一份可评审的文件里，
  让合规审查者一眼看完所有授权。这是 `manifest.yaml`。
* **流程**——大段专业文本。一份完整的骨科问诊协议有几百行，塞进 YAML 标量就不可读，
  而这恰恰是最需要临床评审的部分。

所以技能也可以是一个目录 + 一份 `SKILL.md`：YAML frontmatter 放策略，markdown 正文放流程。
这个布局与 Grok Build、Claude Code 相同，所以同一份文件在几个 harness 之间可移植。

### 优先级（高到低）

1. `$YAOBI_SKILL_PATH` 与 `--skill-dir`
2. `./.yaobi/skills/`（本地覆盖）
3. `yaobi_harness/skills/library/`（随包发布）
4. `manifest.yaml`

同 `skill_id` 高优先级**替换**低优先级。这让医院能钉住自己的问诊协议而不用改包，
也让 `skill build-expert` 能覆盖占位的专家技能。

发现不会自行扩大能力：`allowed_tools` 声明什么，仍由 `CapabilityBroker` 按角色与风险模式校验。
`consult_mode` 写错会**报错而不是忽略**——把 typo 变成静默更宽的授权，
是策略文件唯一不能有的失败模式。

### 随包发布的四份

| 技能 | 内容 |
| --- | --- |
| `yaobi.interview` | 十问歌 + 骨科专科问诊全流程；红旗五条表、节段定位表、跛行鉴别表 |
| `yaobi.vision_read` | 七类图片各自的判读要点与边界 |
| `yaobi.consult_panel` | 五个专科视角 + 14 组用药风险核对表 |
| `yaobi.osteoporosis_risk` | FRAX 要素、椎体骨折线索、治疗顺序硬约束、跌倒风险 |

```bash
python -m yaobi_harness skill list          # 全部技能与来源
python -m yaobi_harness skill show yaobi.interview   # 完整流程文本
```

## 已知限制

* 成员并行是顺序执行的（stdlib-only，无并发编排）；五个成员意味着五次串行往返。
* Persona 的 `inputs`/`outputs` 契约目前是**声明性**的：父层用它决定给成员看什么，
  但不强制校验成员真的产出了声明的字段（`hard_requirements` 只管 schema 层）。
* 分歧只被记录与呈现，没有自动的裁决机制——这是刻意的：分歧的处理应该由人做。
* 会诊意见不进入 `release_status` 计算，只能升级风险模式与追加关切。
