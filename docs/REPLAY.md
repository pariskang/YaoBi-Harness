# 重放日志：让过去的决策可以被离线复核

## 检查点不够

检查点记录的是**状态曾是什么**，但临床审计要问的不是这个。要问的是：

> 在**恰好这些证据**之下，为什么放行了那条建议？

回答这个问题必须用当时的工具返回和当时的模型输出重跑一遍，而不是用今天的端点重跑一遍。
指南库更新了、模型换了版本、说明书改了——今天重跑得到的答案，回答的是另一个问题。

所以每一次**宿主调用**（工具执行 + 模型补全）都按 `(seq, kind, req_hash, result)`
追加到一份 JSONL 日志里。

## 三个用途

1. **审计重放** —— 评审者或监管方可以**完全离线**、不需要任何端点、不需要配置模型，
   重新推导出当初那个结论，并得到同一个答案。
2. **偏离检测** —— 如果重放在某个序号发出了**不同的调用**，日志会拒绝，而不是悄悄把
   一个不匹配的结果塞回去。这能抓到：模型被换掉、工具读了系统时钟、代码改动改变了调用顺序。
   这些情况下"重放成功"是最危险的假象。
3. **廉价回归用例** —— 从真实运行录下的日志本身就是 fixture，生产上发现的 bug
   不用手写桩就能变成测试。

## 用法

```bash
# 录制
python -m yaobi_harness run --complaint "腰痛3月，久坐加重，右下肢麻木" --role physician \
  --facts '{"medications":["布洛芬","华法林"],"conditions":["elderly"]}' \
  --allow-prescription --journal ./audit/case-2026-07-26.jsonl

# 看日志里有什么
python -m yaobi_harness journal ./audit/case-2026-07-26.jsonl --entries

# 离线重放（不需要网络，不需要配置模型）
python -m yaobi_harness run --complaint "腰痛3月，久坐加重，右下肢麻木" --role physician \
  --facts '{"medications":["布洛芬","华法林"],"conditions":["elderly"]}' \
  --allow-prescription --replay ./audit/case-2026-07-26.jsonl
```

环境变量同样可用：`YAOBI_JOURNAL=<path>` 录制，`YAOBI_JOURNAL_REPLAY=<path>` 重放。

**重放偏离时退出码为 3。** 一个把退出码当作"重放确认了原决策"的脚本，
不能在偏离时被告知"是"。

## 日志不是授权

这是最重要的一条边界：**授权在重放时重新推导，不从日志里读。**

`ToolRegistry.call` 先过 `CapabilityBroker.allow`，**之后**才查日志。所以：

* 以医师身份录制的日志，在以患者身份重放时**拿不到**方剂检索结果——
  经纪在触及记录之前就拒绝了；
* 被拒绝的调用**不消耗**日志条目，所以后续调用仍然对齐；
* 被篡改的日志最多让重放**偏离**（并且大声报错），不可能把草案提升为已签名处方。

放行状态同样由状态机重新推导，不从日志恢复。

## 偏离必须响亮

这里有一个不显眼但关键的实现问题。

Agent 会用宽泛的 `except Exception` 包住模型调用，以便在模型故障时回退到确定性路径——
这是对的。但它会把 `JournalDivergence` 也吞掉，于是一次**失败的重放**看起来只是
"模型不可用，已回退规则"的普通告警。

所以日志把偏离**锁存**下来（`Journal.divergences`），运行结束后 `_check_replay_fidelity`
检查这个锁存位并**故障关闭**：

> 重放偏离：日志第 N 条记录的是 X，本次运行发出的是 Y。日志、代码或模型已变化，
> 本次重放不能作为对原决策的复核。

不依赖异常穿透那些合法的 catch，是这个机制能成立的原因。

## 日志耗尽 ≠ 偏离

两者处理不同：

* **偏离**（同一序号上调用不同）→ 硬失败，故障关闭。
* **耗尽**（日志用完了，还有新调用）→ 记 `live_after_exhaustion` 并告警
  "本次结果不是纯离线重放"。离线重放（未配置模型）时，模型调用耗尽会直接报错，
  因为静默降级为确定性路径会掩盖这个缺口。

## 模型名是内容地址的一部分

请求哈希包含模型名，所以**用另一个模型重放会被判为偏离**——这是想要的行为。

但离线重放没有活的客户端可问模型名。所以录制时把 `llm_model` / `llm_provider` /
`llm_available` / `panel_concurrency` 写进日志的 `_meta`，重放时采用记录的名字。

`llm_available` 也很关键：**没有配置模型的录制不含任何 llm 条目**，
重放就必须报告"模型不可用"，否则 Agent 会走一条录制时从未走过的自主路径，
并用一次从未发生过的调用把日志耗尽。（第一版正是这样错的。）

## 并发会诊与日志顺序

并发会诊时，调用**序号取决于完成顺序**。同一份日志重放时要用同样的
`panel_concurrency`（记录在 `_meta` 里，`journal --entries` 会显示）。

`_meta` 里写的是**实际生效的线程数**，不是一个待解析的 `None`：并发是
`YaobiGraphRunner(panel_concurrency=N)` 的构造参数，在写 `_meta` 之前就已解析完成。
`YAOBI_PANEL_CONCURRENCY` 仍是默认值来源，但不再是唯一通道——控制台要同时服务几个操作者，
每次请求去改 `os.environ` 是竞态。

要得到顺序完全确定的日志，用 `YAOBI_PANEL_CONCURRENCY=1` 录制，
或 `--panel-concurrency 1`。

## 在控制台里复核

控制台的「单次运行」页勾选**录制可复核日志**后会多出一个**离线复核**标签页：

* **原样复核** —— 用录制的日志重新推导，并逐项对照放行状态、风险模式、规划来源、
  任务状态、按台账顺序的证据。时间戳与 run_id 被刻意排除在对照之外，
  它们必然不同，比对它们会把每一次重放都报成偏离。
* **"已复现"的判定比"没有偏离"更严** —— 还要求 `live_after_exhaustion == 0`。
  日志耗尽后实跑的尾部是**重新推导**而不是重放，不能算复现。
* **改写主诉再复核** —— 这才是审计真正想问的问题："如果病史读起来不一样，
  这份日志还能支撑那个结论吗？"日志按请求内容寻址，所以答案是响亮的失败，
  并列出偏离的请求哈希。

控制台的日志**只存在内存里、从不落盘**（`Journal(mode="record")`，`path` 为 `None`），
保留最近 20 次；理由和它不持久化聊天记录相同——都是临床内容。
落盘要用 CLI 的 `--journal`，那时留存与访问要求由你自己决定。

> 注意：并发只影响**日志的调用顺序**，不影响**证据台账**——
> 台账在合议后按会诊名单顺序合并，见 [PANEL.md](PANEL.md)。

## 上限与损坏处理

| 情况 | 处理 |
| --- | --- |
| 文件 > 64 MB | 拒绝加载 |
| 条目 > 10000 | 拒绝加载；录制时超限直接报错 |
| 末行残缺（运行被杀） | 截断末行，前面的条目正常加载 |
| 更早的行损坏 | 报错，不加载 |
| 序号不连续（1,3,…） | 报错——有缺口意味着条目丢失，越过缺口重放会把错误结果喂给某次调用 |
| 条目内容不是对象 | 变成一个**失败的**工具结果，运行按工具失败处理并故障关闭 |
| 重复录制到同一路径 | 先截断——追加会产生非连续序号 |

## 已知限制

* **日志包含工具返回的全部数据**，其中可能有假名化病例字段。日志因此与检查点同级敏感，
  按同样的留存与访问要求处理。图片不会进日志（视觉工具只返回结构化所见与 sha256）。
* 只记录宿主调用。运行内部的纯计算（红旗筛查、剂量校验、放行状态机）不记录，
  因为它们是确定性的——但这也意味着**代码变更会导致偏离**，这是特性而不是缺陷。
* 没有签名或防篡改机制。日志能证明"这次重放与记录一致"，不能证明"记录未被修改"。
  需要后者时应在存储层加签名。
