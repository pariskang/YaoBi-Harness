# 视觉模块：临床图片判读

> **改动（本版）**：**模型可以自己要图**。它调用 `request_image`（或在 `ask_patient` 里带
> `image_requests`），界面随即打开上传模块、预选好类型，并展示模型给的理由。
> 什么时候值得要写在 `yaobi.interview` 技能说明里：舌象决定辨证、患肢外观提示血管或
> 骨筋膜室问题、报告单翻拍把"患者转述"换成原始记录；什么时候不要：为了完整而收集影像。
>
> 两条边界，都不是对模型判断的限制：
>
> * **去标识化仍由人确认。** `request_image` 的参数里**没有** `deidentified`——
>   模型没看过那个文件，由它断言等于让这项声明失去意义。
> * **未配置视觉模型时请求被拦下并记录。** 上传了也读不了的图，只是白费对方的力气。
>
> 已附上的图片类型会回到下一轮提示词里（`images_already_attached`），
> 所以模型知道自己已经有舌象照片，可以改要影像翻拍而不是重复要同一张。

## 边界先说清楚

**模型判读不是影像报告，永远不是。**

系统把视觉结果记为 `model_reasoning` 等级——这个等级在本系统的 `NON_RELEASABLE_LEVELS` 里，
所以一条视觉所见**永远不能单独支撑任何放行的临床结论**。这不是保守，是证据链的要求：
影像诊断需要完整序列、需要正式阅片、需要签名负责的人。

视觉能做三件真正有价值的事：

1. **描述可见所见**——客观、具体、可核对；
2. **提出急症外观信号**——可以**升级**风险模式；
3. **指出下一步该问什么、该查什么**——这是它对问诊最大的贡献。
   为了让这份贡献落在**当轮**：判读节点排在问诊节点之前，判读所见
   （可疑点、值得追问的问题）直接进入本轮追问的组织材料；而判读本身
   在控制台**上传图片的那一刻**就已在后台开始——用户打完问题时，
   所见通常已经在缓存里，本轮不再为读图付出一次串行的多模态调用。

它不能：给出诊断、给出治疗建议、给出任何剂量、声称替代正式检查。
`ImageFindings` 契约里 `requires_formal_read` 是必填字段，影像类判读把它写成 `false`
会被 schema 直接拒绝（不是靠提示词自律，是靠校验）。

## 配置

默认走 Poe 的 OpenAI 兼容端点，模型 `Gemini-3.1-Pro`：

```bash
export YAOBI_VISION_PROVIDER=poe
export POE_API_KEY=...
export YAOBI_VISION_MODEL=Gemini-3.1-Pro     # 可换任意多模态模型
```

任何 OpenAI 形态的多模态端点都可以——图片作为 `image_url` 内容块以 `data:` URI 传递，
Poe / Azure / LiteLLM / MiniMax 都接受这种形态。未配置时影像工具报告自己不可用，
不会导致整个 harness 起不来。

**没单独配视觉模型时，控制台借用会话自己的对话模型。** 上面这套查找找的是*单独的*
视觉提供方，默认 Poe；用一个 OpenAI 兼容端点起控制台而没设 `YAOBI_VISION_*`，
它就什么也找不到，读图静默关闭——这正是「上传 X 片无法自动解析」的成因：
片子传上去了、`VisionAgent` 也排进了计划，只是它要用的工具从来没被造出来。

既然这套栈说的都是 OpenAI 形状的接口，一个多模态对话模型就是一个能用的视觉模型，
所以现在会把会话的客户端借过来，并在控制台徽章上标明「借用对话模型」。
如果那个模型其实不是多模态的，会在调用时报出提供方自己的错误——那是个**可见的**、
进证据台账的失败，好过猜"大概不支持"然后继续黑着。
显式设了 `YAOBI_VISION_PROVIDER` 却没建起来则不借用：那是一个明确的配置意图没生效，
应当报出来，不该拿别的东西悄悄填上。

### 上传通道

浏览器把 `File` 原样 `POST /api/image/upload`（头里带 `X-Image-Kind` 与
`X-Deidentified: 1`），换回一个 handle，之后每轮聊天只带 handle。
不走 JSON：base64 会涨三分之一，一张 12 MB 的片子变成 16 MB 的请求体，
撞在控制台 256 KB 的信令上限上。上传上限 24 MB，图片本身上限 12 MB。

服务端留的是**原始字节**而不是 base64（省四分之一内存，`data:` URI 用时再拼），
按**总字节数**封顶 60 MB 而不是按张数——张数上限套在大小可变的对象上根本不是上限，
24 张 × 12 MB 就是 288 MB 常驻，Colab 内核会有反应。handle 同时覆盖**内容与类型**：
只按内容取键时，同一张照片先传成 X 线片再传成舌象会撞成一条，后一次会静默改掉前一次的类型。
不落盘。

### 一张图只判读一次

每轮都是一次全新的完整审计运行，这正是"第三轮才说出来的红旗在第三轮就被筛查到"的原因。
但套在图片上，它意味着第二轮附的片子在第三、第四、第五轮又被送去多模态模型一次——
图片是这套系统里**唯一不会变**的输入，重读买不到任何东西，却每轮都要付一次视觉调用的钱。

现在判读结果按附件缓存在会话里（`ConversationSession.image_reads`），后续轮次**重放**
而不重读。结果仍然会进入每一轮的证据台账——引用必须能在做出它的那次运行里解析——
但标注 `carried_forward: true`，说明它来自哪一轮。缓存键是"内容 + 类型"：
舌象判读和 X 线片判读是两个不同的任务、两套不同的提示词，共用一份缓存是错的。

`yaobi.vision_read` 技能在 frontmatter 里声明 `model: Gemini-3.1-Pro`，
所以文本模型跑的运行也能借用视觉模型——这个决定写在被评审的策略文件里，不在代码里。

## 三条不可协商的规则

### 1. 图片不落盘

字节读入 → 编码 → 发出 → 丢弃。留下的只有结构化所见 + 原始字节的 SHA-256。
审计能证明**哪一张**图产生了哪条所见，而仓库从不持有那张图。检查点里也不会有图片。

### 2. 没有去标识化声明就不判读

`medical_image_read` 要求 `deidentified=true`。这是刻意设的减速带，
因为这是最容易带上姓名和住院号的输入通道：手机翻拍的片子经常有姓名、住院号、
出生日期、检查日期、条码、机构名，DICOM 导出截图几乎必然带角标。

控制台里这一步是一个复选框，**它控制的是文件选择器本身**——没勾选就打不开选图，
所以不存在"先上传后声明"的路径。

### 3. 检出身份信息即丢弃全部判读

判读前先做一次独立的 PHI 预检。命中就**丢弃全部所见**，只返回警告与遮盖指引。

拒绝判读在这里是**正确结果**，不是失败：工具返回 `ok=True`（它正常完成了工作），
`phi_detected=True`，`observations=[]`。标记为失败会让熔断器误开，
而这不是工具的故障。

预检本身失败（端点抖动）时既不当作"有 PHI"也不当作"无 PHI"：
判读照常进行，但这一事实被记录下来。把预检故障当作有 PHI 会让每张图都被拒；
当作无 PHI 会静默降低保护。两种都错，所以选择"照做并留痕"。

## 七种图片类型，七套提示词

每类的判读要点和输出契约都不同——"读这张 X 线"和"描述这个舌象"不是一回事，
不能共用提示词。

| 类型 | 关键约束 |
| --- | --- |
| `radiograph` | 翻拍丢失窗宽窗位、引入畸变；**不可判读就写不可判读** |
| `mri_ct` | 单张翻拍不能替代序列阅片，必须写进 `caveat` |
| `tongue` | 舌象只是四诊之一；**色温与白平衡**对舌质颜色影响极大，必须说明 |
| `posture_gait` | 静态照片不能替代体格检查；每条所见都要配"需现场确认什么" |
| `limb_surface` | 最可能出现真急症；肿胀/发紫/张力/坏死必须进 `urgent_signals` |
| `report_document` | **只转录不解释**；看不清写"不可辨认"，**绝不猜数字** |
| `other` | 只描述可见内容，说明能支持什么、不能支持什么 |

`report_document` 的"绝不猜数字"是硬要求：一个猜错的骨密度 T 值或肌酐值会直接
改变用药决策，比没有这个数值危险得多。

## 视觉如何影响运行

**只能加，不能减。** 和红旗筛查、批评者是同一条containment 规则。

`VisionAgent` 把 `urgent_signals` 里的外观描述映射到筛查信号
（发紫/花斑 → 血管；张力/水疱 → 骨筋膜室；红肿/窦道/坏死 → 感染；畸形/成角 → 骨折），
命中就把运行切到急症模式并把信号并入 `intake.screening.hits`。

反过来不成立：视觉说"片子看着没事"**不能**撤销规则已判定的红旗。

## 用法

```bash
# 单张判读
python -m yaobi_harness vision ./xray.jpg --kind radiograph --deidentified \
  --context "68岁女性，腰痛3月，身高变矮"

# 随病例一起跑（可重复 --image）
python -m yaobi_harness run --complaint "左小腿肿胀2天" --role patient \
  --image limb_surface:./leg.jpg

# 对话中附图
python -m yaobi_harness chat --role patient --image tongue:./tongue.jpg \
  --message "腰痛3个月，舌头拍了张照"
```

控制台「对话问诊」左栏可以直接拖入图片（先勾选去标识化）；
判读结果出现在「问诊与会诊」标签页，带 sha256 前缀、可判读性、置信度、
以及固定显示的「需正式阅片」徽章。

`POST /api/chat` 与 `/api/run` 接受 `images: [{kind, ref, deidentified}]`，
`ref` 是 `data:` URI 或本地路径。**缺少 `deidentified` 的载荷被拒绝而不是默认为 true**——
默认为真会让一个忘记勾选的复选框把可识别图片发给第三方模型。

## 已知限制

* 单张翻拍照片的判读价值本就有限；这个模块的正确用法是**帮助问诊与查体决策**，
  不是替代影像检查。
* 没有 DICOM 支持：只处理常见位图格式（PNG/JPG/WEBP/GIF/BMP），上限 12 MB。
* PHI 预检依赖模型的视觉判断，不是 OCR + 正则；它会漏。**它是一层减速带，不是保证。**
  真正的保护是操作者在上传前遮盖。
* 图片不参与证据的可放行性计算，所以一个只有影像支持的结论会被 CitationGuard 拦下——
  这是设计意图，不是缺陷。
